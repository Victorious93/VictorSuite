# victorpc pairing — shared fleet spec v1

Status: **FROZEN v1 (design)**. Nothing here is implemented yet. Producer: **VictorSuite** (`com.termux`)
and the PC script `pc/victor-pc-setup.sh` (both land in later PRs, see `docs/REMOTE_PC_PLAN.md`).
Consumers: **Victorious File Manager** (PC pane) and **droidcommand-AI** (hub tile).

Changes to v1 are additive only (new optional keys / columns / extras). Anything that changes the
meaning of an existing field is v2 and needs a new `v` / `schema_version`.

Words: **MUST**, **MUST NOT**, **SHOULD** as in RFC 2119.

---

## 1. Common encodings

| Name | Format |
|---|---|
| base64url | RFC 4648 §5 alphabet, **no padding** |
| base32 | RFC 4648 alphabet `A–Z2–7`, uppercase, no padding |
| profile id | 12 base32 chars (60 random bits), generated by the PC script, e.g. `7Q2M4KX9TB5N` |
| device id | 16 base32 chars (80 random bits), generated once per VictorSuite install, e.g. `K3VQ7M2XH9PDT4WA` |
| app name | one of `victorsuite`, `filemanager`, `droidcommand` (lowercase `[a-z0-9]+`, from the pins table §8, **never** from the caller) |
| **host key** | `<keytype>:SHA256:<base64-no-pad of SHA-256(key blob)>`, e.g. `ssh-ed25519:SHA256:gHC80Ray5GnftiotQW/JWkdaUZrT2zhJoAgvVkpna9w`. `<keytype>` is the SSH key type name (`ssh-ed25519`, `ecdsa-sha2-nistp256`, `rsa-sha2-512` is **not** a key type — RSA keys are `ssh-rsa`). The base64 part is standard base64 (with `+` `/`), padding stripped — the same string OpenSSH prints after `SHA256:`. |
| host key list | host keys joined with `;`, no spaces, order not significant |
| public key | `<keytype> <base64 blob>` (OpenSSH `authorized_keys` form) with **no comment** |

The **same host-key form** is used in the QR (`hk`), the enrollment response, the provider
(`host_keys`) and the enroll-service reply. A client MUST compare host keys by exact string match
after splitting on `;`.

## 2. QR payload (`victorpc://pair`)

A URI, query string percent-encoded per RFC 3986. `+` in values MUST be sent as `%2B`;
parsers MUST NOT decode `+` as space.

| Key | Required | Type | Rules |
|---|---|---|---|
| `v` | yes | int | `1`. Any other value → refuse ("update VictorSuite"). |
| `id` | yes | profile id | 12 base32 chars. |
| `n` | yes | string | Display name, 1–64 UTF-8 chars, no control chars. |
| `u` | yes | string | Login user, POSIX name `[a-z_][a-z0-9_-]{0,31}`. |
| `h` | yes | list | 1–8 hosts, `,`-joined, **preferred connect order** (LAN first, then tailnet). Each is an IPv4 literal, a bracketed IPv6 literal, or a DNS name (`*.local`, MagicDNS `*.ts.net`, plain hostname). Hints only — identity is `hk`. |
| `p` | yes | int | sshd port, 1–65535 (normally 22). |
| `hk` | yes | host key list | All sshd host keys the script found (§1). At least one. |
| `pp` | yes | int | Pairing listener port, 1024–65535 (default 47022). |
| `t` | yes | base64url | 16-byte one-time token (22 chars). |
| `x` | yes | int | Token expiry, Unix epoch **seconds**. Script default: now + 600. Client refuses if `x` is in the past by its own clock (allow 120 s skew). |
| `cap` | no | list | `,`-joined from `sftp`, `adb`. Unknown values ignored. Default empty. |

Unknown keys MUST be ignored. Duplicated keys → refuse.

Example (throwaway values, same as the test vector in §4):

```
victorpc://pair?v=1&id=7Q2M4KX9TB5N&n=don-ubuntu&u=don&h=192.168.1.42,don-ubuntu.local,100.101.7.12&p=22&hk=ssh-ed25519:SHA256:gHC80Ray5GnftiotQW/JWkdaUZrT2zhJoAgvVkpna9w&pp=47022&t=AAECAwQFBgcICQoLDA0ODw&x=1762755600&cap=sftp
```

### 2.1 Manual-code fallback (headless PC)

The script always prints, next to the terminal QR (`qrencode -t ansiutf8`) and a PNG:

```
Pairing code:  7Q2M-4KX9-TB5N / H7KD-2MQX-9P
Host key:      ssh-ed25519:SHA256:gHC80Ray5GnftiotQW/JWkdaUZrT2zhJoAgvVkpna9w
Listening on:  192.168.1.42:47022, 100.101.7.12:47022  (expires 00:40 EST)
```

- First group = profile id (12 chars), second = **manual key**: 10 base32 chars (50 bits).
- Input is normalized: uppercase, remove `-` and spaces, map `0→O`, `1→I`, `8→B` before validation.
- The phone finds the host via discovery (or Don types an IP), connects to the pairing port
  (default 47022; the manual form accepts `host:port`), and runs §3 with the manual key.
- In manual mode the phone does not know `hk` in advance: it learns it from the authenticated
  response (§3) and MUST show it for Don to compare against the PC screen before saving.
- The manual key is only usable online against the live listener (single use, 3 tries), which is
  why 50 bits is enough.

## 3. Enrollment transcript (one-shot listener)

Transport: plain TCP to `<host>:<pp>`. Each side sends **one** JSON object as a single UTF-8 line
terminated by `\n`, max 8192 bytes. The listener binds only the LAN and tailnet addresses listed in
`h` (never `0.0.0.0` / `::`), and exits on the first success, after 3 failed MACs, or at `x`.
Both the QR token and the manual key are consumed by the first success.

**HMAC key `K`:** QR mode → the 16 raw bytes of `t`. Manual mode → the ASCII bytes of the
normalized 10-char manual key.

All HMACs are HMAC-SHA256, output encoded base64url. Fields inside the transcripts are joined
with `|` (0x7C); no field may contain `|`, `\r` or `\n` (validated before signing).

**Request (phone → PC):**

```
C   = "victorpc-v1|c|" + id + "|" + dev + "|" + app + "|" + pub + "|" + nc
mac = base64url(HMAC-SHA256(K, ASCII(C)))
{"v":1,"id":"<id>","dev":"<device id>","app":"<app name>","pub":"<public key>","nc":"<nc>","mac":"<mac>"}
```

`nc` = 16 random bytes, base64url (22 chars). `pub` MUST be `ecdsa-sha2-nistp256` in v1
(Android Keystore P-256; see plan §3). The listener also accepts `ssh-ed25519` for future consumers.

**Listener checks:** `v == 1`, `id` matches, token not expired/used, `pub` parses, constant-time MAC
compare against K (QR) **or** K (manual). On success it appends exactly one line to
`~<u>/.ssh/authorized_keys` (creating the dir 0700 / file 0600, owned by `<u>`):

```
restrict,pty[,port-forwarding,permitopen="<container-ip>:5555",permitopen="<container-ip>:7007"] <pub> victorpc:<dev>:<app>
```

The bracketed part is present only when the script detected Waydroid/AVD and Don enabled ADB
(plan §5). An existing line with the same comment is replaced, not duplicated.

**Response (PC → phone):**

```
S    = "victorpc-v1|s|" + id + "|" + nc + "|" + fp(pub) + "|" + hk
mac2 = base64url(HMAC-SHA256(K, ASCII(S)))
{"v":1,"ok":true,"hk":"<host key list>","mac":"<mac2>"}
```

`fp(pub)` = the public key in host-key form (§1), `hk` = the host key list exactly as in the QR.
Error replies are **unauthenticated** and only tell the client to stop:
`{"v":1,"ok":false,"err":"bad_request|bad_mac|expired|used|too_many_attempts|internal"}`.

**Client checks:** verify `mac2` (constant time). QR mode: the `hk` set MUST equal the QR `hk` set.
Then the client MUST make a real SSH login with the new key, with the host key pinned to `hk`
(StrictHostKeyChecking), before saving the profile. Any mismatch → discard, nothing saved.

## 4. Stored profile (on the phone)

Public data only. The private key never leaves Android Keystore and is non-exportable.
VictorSuite's own key alias: `victorpc.<profileId>.victorsuite`. VictorSuite's
`termux-keystore` (embedded Termux:API) refuses aliases starting with `victorpc.` — that guard
protects **VictorSuite's** Keystore only. A consumer stores its own key in **its own** app's
Keystore under `victorpc.<profileId>.<app>`.

Profiles and keys are excluded from `config.export` key material: an export carries the public
profile only and pairing must be redone on a new phone.

## 5. `PcProfileProvider` (read-only)

- Authority: **`com.termux.victor.pc`** (exported, no `readPermission`; access is checked in code, §8).
- `content://com.termux.victor.pc/profiles` → all profiles (MIME `vnd.android.cursor.dir/vnd.com.termux.victor.pc.profile`)
- `content://com.termux.victor.pc/profiles/<profile_id>` → one row or empty (MIME `vnd.android.cursor.item/vnd.com.termux.victor.pc.profile`)
- `insert` / `update` / `delete` / `openFile` → `UnsupportedOperationException`. `projection`,
  `selection` and `sortOrder` are ignored (all columns, order = `paired_at` ascending).

| Column | Type | Notes |
|---|---|---|
| `schema_version` | INTEGER | `1` |
| `profile_id` | TEXT | §1 |
| `name` | TEXT | display name |
| `user` | TEXT | login user |
| `hosts` | TEXT | `,`-joined, preferred order (same rules as QR `h`) |
| `port` | INTEGER | sshd port |
| `host_keys` | TEXT | host key list (§1), the pin |
| `caps` | TEXT | `,`-joined (`sftp`, `adb`), may be empty |
| `paired_at` | INTEGER | epoch **ms** |
| `last_seen_host` | TEXT | nullable; the host from `hosts` that last answered with a pinned key |
| `last_seen_at` | INTEGER | nullable; epoch ms |
| `reachable` | INTEGER | `1` reachable at last check, `0` not, `-1` unknown / not checked this session |
| `caller_enrolled` | INTEGER | `1` if the **calling** app has its own key enrolled for this profile, else `0` |

There is **no** column with a token, private key, password, agent socket path or proxy address.
`reachable` is a cached value; VictorSuite does not probe on query.

`call(method = "consent_status", arg = null, extras = null)` → Bundle `{ "consent": "granted" | "required" }`
for the caller. A caller that passes the pin check but has no consent gets **zero rows** from
`query` (never a `SecurityException`) and should start §7's consent flow.
A caller that fails the pin check gets `SecurityException` from every method.

Change notifications: `notifyChange` on `content://com.termux.victor.pc/profiles` when a profile is
added, removed, re-paired, or `reachable` changes. Consumers MAY register a `ContentObserver`.

## 6. `PcEnrollService` (Messenger, bound)

Messenger (Bundle-based) rather than AIDL, so consumers need no shared `.aidl` file.

- Bind: `Intent("com.termux.victor.pc.action.ENROLL").setPackage("com.termux")`, `BIND_AUTO_CREATE`.
  The service checks the caller (§8) on every message with `Binder.getCallingUid()`
  (`Message.sendingUid` on API 22+).
- Request `what = 1` (`MSG_ENROLL`), `replyTo` required, `data`:

| Key | Type | Required | Notes |
|---|---|---|---|
| `v` | int | yes | `1` |
| `request_id` | String | yes | ≤ 64 chars, echoed |
| `profile_id` | String | yes | |
| `public_key` | String | yes | §1 public key form, no comment. `ecdsa-sha2-nistp256` or `ssh-ed25519`. |

- Request `what = 3` (`MSG_REVOKE`): `v`, `request_id`, `profile_id`. Removes the caller's
  `victorpc:<dev>:<app>` line from the PC.
- Reply `what = 2` (`MSG_RESULT`), `data`:

| Key | Type | Notes |
|---|---|---|
| `v` | int | `1` |
| `request_id` | String | echoed |
| `ok` | boolean | |
| `host_keys` | String | on success: host key list (§1) to pin |
| `key_comment` | String | on success: `victorpc:<dev>:<app>` that was written |
| `error` | String | on failure, one of the codes below |

What VictorSuite does on `MSG_ENROLL`: log in to the PC with **its own** key (host key pinned), add
`restrict <public_key> victorpc:<dev>:<app>` to `~/.ssh/authorized_keys` (replacing a line with the
same comment), verify, and reply. `<app>` comes from the pins table, never from the request.
Consumer keys get plain `restrict` (SFTP and a shell work; no forwarding).

| Error code | Meaning |
|---|---|
| `bad_request` | missing/invalid field or `v` |
| `not_allowed` | caller failed the pin check (§8) |
| `consent_required` | pinned, but Don has not approved this app (start §7 consent) |
| `unknown_profile` | no such `profile_id` |
| `bad_key` | key type not allowed or blob invalid |
| `unreachable` | no host in `hosts` answered |
| `host_key_mismatch` | PC answered with a key not in `host_keys` → hard stop, re-pair needed |
| `server_refused` | PC refused VictorSuite's own key (re-pair VictorSuite) or the write failed |
| `busy` | another enroll for the same profile is running |
| `internal` | anything else |

Rate limit: 5 requests per caller per minute. Every request is written to the My PC audit log
(JSONL: time, caller package, cert SHA-256, op, profile, result).

## 7. Intents

### 7.1 `OPEN_PC`

- Action **`com.termux.victor.action.OPEN_PC`**, target package `com.termux`, exported activity.
- Extras:

| Extra | Type | Required | Values |
|---|---|---|---|
| `profileId` | String | yes | a `profile_id` |
| `mode` | String | yes | `"terminal"` or `"sftp"` (v1). `"mirror"` is **reserved** (§7.3); v1 returns `unsupported_mode`. |
| `path` | String | no | `sftp` only: absolute remote start directory. Default: the user's home. Ignored for `terminal`. |

- Caller identity: use `startActivityForResult` (or an `ActivityResultLauncher`) so
  VictorSuite can read `getCallingPackage()`. VictorSuite re-checks the pin **and** consent on every
  launch. If there is no calling package (plain `startActivity`), VictorSuite shows its own
  "Open <name> (<mode>)?" confirm screen and only continues on Don's tap.
- Result: `RESULT_OK` once the terminal session / SFTP browser is open in VictorSuite (the user is
  now in VictorSuite). `RESULT_CANCELED` with String extra `error` ∈ `bad_request`,
  `not_allowed`, `consent_required`, `unknown_profile`, `unsupported_mode`, `unreachable`,
  `host_key_mismatch`, `user_cancelled`.
- A host-key mismatch always shows VictorSuite's hard-stop screen (no "accept anyway"), whatever the caller.

### 7.2 Consent

- Action **`com.termux.victor.action.PC_CONSENT`**, target package `com.termux`, started **for
  result** by a pinned consumer. VictorSuite shows "Allow <app label> to see your PCs and add its own
  key?". `RESULT_OK` = granted, `RESULT_CANCELED` = declined. Revocable in My PC → Connected apps.

### 7.3 Mirroring handoff (droidcommand-AI hub tile)

The existing scrcpy client activity **`com.termux.victor.scrcpy.MainActivity`** exists in the repo
(`app/src/main/java/com/termux/victor/scrcpy/MainActivity.java`, declared at
`app/src/main/AndroidManifest.xml:243`). Verified facts:

- It is **not exported** (no `android:exported`, no intent-filter), so another app **cannot**
  launch it directly.
- It reads no intent extras; the device address comes from an EditText / its own SharedPreferences.
- `SendCommands.java:123` connects ADB to `<ip>:5555` (hard-coded port) and `Scrcpy.java:142`
  opens the video socket to `<ip>:7007`.

So the handoff is **via `OPEN_PC` with `mode="mirror"`** (reserved in v1, implemented with plan PR 9):
VictorSuite opens SSH local forwards `127.0.0.1:5555 → <container-ip>:5555` and
`127.0.0.1:7007 → <container-ip>:7007` (the `permitopen` entries in §3), then starts its own scrcpy
activity pointed at `127.0.0.1`. Whether the scrcpy server path works unchanged through the forward is
**unverified**. droidcommand-AI MUST NOT target the scrcpy class.

## 8. Caller trust and consumer pins

Fleet APKs are signed with **different** keys, so a `protectionLevel="signature"` permission cannot
cover them. Every provider/service/intent entry point instead does, per call (same model as
`FleetThemePins` / `remotecontrol/TrustModel.kt`):

1. `Binder.getCallingUid()` (or `getCallingPackage()` for activities) → package(s). Shared-UID or
   more than one package → refuse.
2. The package MUST be in the table below and have **exactly one** signer whose SHA-256 is pinned
   and not revoked. A blank or TBD pin **never** authorizes. There is no "next" key in v1.
3. For provider queries: repeat 1–2 after building the cursor; if it changed, return nothing.
4. Consent (§7.2) for everything except `consent_status`.

| Package | Build | Signer SHA-256 | App name | v1 rights |
|---|---|---|---|---|
| `ai.droidcommand.app` | debug key | `88:00:51:A6:D9:5D:38:DD:8D:81:E1:93:1E:17:05:48:03:87:D5:93:C3:09:43:53:99:68:E6:EF:11:A0:C8:4D` | `droidcommand` | read provider, launch `OPEN_PC`. **Holds no key; may not call `PcEnrollService`.** |
| `ai.droidcommand.app` | release | TBD — **not pinned** | — | none until published |
| `ai.victorious.filemanager` | release | `7C:6E:37:61:21:9D:81:9A:66:B3:17:93:C7:AB:E6:25:A5:B7:DC:10:67:16:FB:0D:6C:48:56:BF:72:26:CB:3C` | `filemanager` | read provider, enroll/revoke own key, `OPEN_PC` |
| `ai.victorious.filemanager.debug` | debug | `8C:1F:E3:C9:E5:34:F2:71:05:C0:68:8F:45:28:D7:7E:47:11:AE:0A:79:DD:08:D1:E8:59:30:B9:E9:48:85:F2` | `filemanager` | same as release |

These cert values were **reported by those apps' bots and have not been independently verified**
against the APKs. Verify each with `apksigner verify --print-certs` before PR 8 ships.

**Open item:** VictorSuite already launches DroidCommand as either `ai.droidcommand.app` or
`ai.droidcommand.app.debug` (`app/src/main/java/com/termux/victor/droidcommand/DroidCommandAi.kt:20`).
The pin above is reported for `ai.droidcommand.app`. If the debug build is actually
`ai.droidcommand.app.debug`, that package is **not pinned** until its own cert is confirmed — do not reuse
this pin for it.

## 9. Remote access (Tailscale) — what consumers may rely on

- VictorSuite's default remote path is its built-in userspace `tailscaled`, which exposes a
  SOCKS5/HTTP proxy on `127.0.0.1:1055` (`HeadscaleClickConfig`). The official Tailscale app (system
  VPN) is also supported and auto-detected. LAN works with Tailscale off.
- **The `127.0.0.1:1055` proxy is NOT a fleet contract in v1.** Any local app can connect to a
  loopback port, so it is not access-controlled; it is a VictorSuite-internal detail and may move,
  change protocol, or require auth later without a spec change.
- Consumers that need to reach the PC remotely SHOULD rely on the official Tailscale app being
  connected, or SHOULD open the session through `OPEN_PC` so VictorSuite picks the path.

## 10. Security invariants (all parties)

- Never expose SSH, ADB or VNC to the internet: no router port forwards, no UPnP; firewall rules are
  scoped to the LAN subnet and `100.64.0.0/10` / `tailscale0`.
- Host keys are pinned at pairing; a changed key is a **hard stop** with no override. Fix = re-pair.
- Tokens are single-use, expire (`x`), and the listener stops after 3 bad MACs.
- No secret (token, private key, password) is ever written to the repo, a log, a provider row, a
  backup/export, or the clipboard.
